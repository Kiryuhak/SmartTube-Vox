# Жизненный цикл токена Яндекс ID

Источники: [Device Flow](https://yandex.ru/dev/id/doc/ru/codes/screen-code-oauth), [обновление токена](https://yandex.ru/dev/id/doc/ru/tokens/refresh-client), [сроки действия](https://yandex.ru/dev/id/doc/ru/concepts/ya-oauth-intro), [отзыв](https://yandex.ru/dev/id/doc/ru/tokens/token-invalidate).

Яндекс документирует `expires_in` в ответе Device Flow и может выдавать `refresh_token`. Фактический срок access token для текущего OAuth-приложения зависит от его настроек и разрешений; без успешного реального обмена он неизвестен. Для долгосрочного автоматического входа следует предусмотреть refresh. Запрос обновления требует `client_id` и `client_secret`, а ответ может содержать новый refresh token. При обновлении нужно атомарно заменять оба токена; `invalid_grant` означает необходимость повторного входа. Локальный выход удаляет токен, а серверный отзыв потребует отдельного backend-вызова с учётными данными приложения.

Предлагаемый контракт: `POST /oauth/yandex/refresh` с JSON `{"refresh_token":"...","request_id":"UUID"}`. Сервер принимает только эти поля, ограничивает размер тела, использует фиксированный `https://oauth.yandex.ru/token`, `grant_type=refresh_token`, серверные `client_id` и `client_secret`, ограничение частоты и timeout. Ответ с `Cache-Control: no-store` возвращает нормализованное состояние; при успехе — access token, новый refresh token и `expires_in`. Тела и заголовки с токенами не логируются и не отправляются в аналитику. Токены не сохраняются на сервере. `invalid_grant` завершает автоматическое обновление; временные ошибки получают ограниченный retry.

Текущий `VotData` сохраняет access token в обычном `SharedPreferences` и не хранит refresh token. Поэтому endpoint и хранение refresh token **ещё не реализованы**. Перед включением долгосрочного входа нужен отдельный аудит Android-хранилища: защищённое локальное хранение refresh token, атомарная замена пары токенов, очистка при logout и миграция/ошибки восстановления. Брокер и реальный OAuth-клиент пока не развернуты; debug mock success проверяет только клиентский путь сохранения access token, а не срок действия или refresh.

## Локальный mock

Из каталога сервиса: `MOCK_SCENARIO=pending_slow_success node dev/mock-server.mjs` (PowerShell: `$env:MOCK_SCENARIO='pending_slow_success'; node dev/mock-server.mjs`). Затем `adb reverse tcp:8787 tcp:8787` и debug сборка `-PyandexOAuthBrokerUrl=http://127.0.0.1:8787`. Для localhost debug клиент также берёт фиктивный device code из `/dev/device/code`; для HTTPS-брокера он обращается к Яндексу напрямую за кодом. Другие сценарии: `expired`, `invalid_client`, `network_error`, `rate_limited`, `pending`. Сценарий можно переключить локальным `POST /dev/scenario/<имя>`, при этом счётчик poll обнуляется. Mock использует фиктивный токен; его нельзя считать подтверждённой авторизацией Яндекса.
