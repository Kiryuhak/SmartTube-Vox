# SmartTube VOX 8 — Стратегия Controlled Live Backend и Архитектура Live Translation

## 1. Архитектурный контекст и выводы исследований (Patch #2 – Patch #4)

В ходе исследований Patch #2 («Translation 2.0 Architecture Audit») и Patch #3 («Live Translation Protocol Investigation») было установлено:
1. **Текущий статус публичного API перевода**:
   - `LIVE_BACKEND_CAPABILITY: VOD_ONLY`.
   - Протокол основан на HTTP polling с передачей VOD URL (`POST /api/v1/translate` + `GET /api/v1/status`).
   - Отсутствуют: WebSocket, gRPC, HTTP Chunked Transfer, сессионная инкрементальная догрузка аудио.
2. **Архитектурный тупик прямого обращения клиента к провайдеру**:
   - Клиент SmartTube (Android TV / Tizen) не может напрямую вызывать сторонние API машинного перевода стримов из-за необходимости защиты закрытых API-ключей, валидации прав, лимитов пропускной способности и отсутствия стандартного единого формата живого аудиопотока у разных провайдеров.
   - Зашивание токенов или приватных ключей внешних сервисов в клиентский APK строго запрещено политикой безопасности и стандартом Zero-Telemetry.
3. **Решение**: переход к архитектуре **Controlled Live Backend / Proxy Gateway**, где серверная инфраструктура SmartTube VOX берет на себя роль оркестратора сессий живого перевода, буферизации сегментов и взаимодействия с движками ASR (распознавание речи), MT (машинный перевод) и TTS (синтез речи).

## 2. Концепция Controlled Proxy Gateway

Архитектура сквозного конвейера живого перевода:

```
+---------------+                      +------------------------+                     +------------------------+
|  SmartTube    |   1. Handshake       |    SmartTube VOX       |   3. Stream ASR     | Third-Party AI Engine  |
|  Client (TV)  | -------------------> |    Live Backend        | ------------------> | (Yandex / Whisper /    |
|               | <------------------- |    (Gateway/Proxy)     |                     |  DeepL / ElevenLabs)   |
|               |   Session Created    +------------------------+                     +------------------------+
|               |                                  |                                               |
|               |   2. Audio Segments              |                                               |
|               |   (Opus / AAC chunks)            |                                               |
|               | -------------------------------> | Ingestion Buffer                              |
|               |                                  |                                               |
|               |                                  | 4. Translation Queue                          |
|               |                                  |    & Worker Pool                              |
|               |                                  | <---------------------------------------------+
|               |                                  |    Synthesized Speech (TTS Audio Chunks)
|               |   5. Stream Translated Chunks    |
|               | <-------------------------------+
|               |
| TV Translated |
| Buffer (15s)  |
| -> AudioTrack |
+---------------+
```

### Ключевые компоненты:
1. **Live Session Coordinator**:
   - Управляет жизненным циклом сессии перевода прямого эфира.
   - Выполняет handshaking, выдает временный `sessionId` со строгим TTL (30–60 минут активности).
2. **Segment Ingestion Service**:
   - Принимает нарезанные клиентом аудиосегменты ( длительностью 2.0 – 4.0 сек, формат Opus 48 kHz / AAC).
   - Проверяет целостность, монотонность таймкодов и порядковых номеров (`seq_num`).
3. **Translation Worker Queue**:
   - Очередь задач в памяти (Redis / in-memory RingBuffer) для передачи аудио в модуль распознавания и перевода.
   - Пул воркеров с динамическим масштабированием и тайм-аутами (не более 2.5 сек на обработку сегмента).
4. **Translated Segment Delivery Service**:
   - Раздает готовые синтезированные аудиосегменты клиенту по протоколу HTTP/2 Server Push, WebSocket либо через компактный HTTP chunk polling с минимальной задержкой.

## 3. Контракты взаимодействия (Client-to-Backend API)

### 3.1. Создание сессии (`POST /v1/live/session/create`)
**Запрос**:
```json
{
  "sourceLanguage": "en",
  "targetLanguage": "ru",
  "audioCodec": "opus",
  "sampleRate": 48000,
  "chunkDurationMs": 2000,
  "clientTimestampMs": 1728259200000
}
```
*Примечание*: Запрос **не содержит** URL видео, videoId, заголовков видео или аккаунтов пользователя (Zero-Telemetry).

**Ответ (201 Created)**:
```json
{
  "sessionId": "vox_live_9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
  "expiresAtMs": 1728262800000,
  "targetOffsetMs": 15000,
  "ingestEndpoint": "/v1/live/session/vox_live_9b1deb4d.../ingest",
  "streamEndpoint": "/v1/live/session/vox_live_9b1deb4d.../stream"
}
```

### 3.2. Передача аудиосегмента на перевод (`POST /v1/live/session/{sessionId}/ingest`)
- **Headers**:
  - `Content-Type: application/octet-stream`
  - `X-Vox-Seq: 104`
  - `X-Vox-Pts-Ms: 208000`
  - `X-Vox-Duration-Ms: 2000`
- **Body**: Сырой аудиоконтейнер (Opus в WebM/OGG или ADTS AAC).
- **Размер тела**: ~16–48 КБ на 2-секундный сегмент.
- **Ответ (202 Accepted)**:
```json
{
  "receivedSeq": 104,
  "status": "QUEUED",
  "estimatedReadyMs": 1800
}
```

### 3.3. Получение переведенного аудио (`GET /v1/live/session/{sessionId}/stream`)
- **Протокол**: HTTP chunked stream или WebSocket.
- Каждое сообщение содержит бинарный аудио-чанк с метаданными синхронизации:
  - `seq`: 104
  - `ptsMs`: 208000
  - `durationMs`: 2100 (с учетом темпа речи TTS)
  - `payload`: MP3 / Opus audio bytes.

## 4. Требования к серверной безопасности и защите от злоупотреблений

Серверный прокси не должен функционировать как открытый публичный релей (Open Proxy).

1. **Строгие лимиты (Rate Limiting & Throttling)**:
   - Не более 1 активной сессии на IP/клиентский токен.
   - Ограничение частоты загрузки: не более 1 сегмента в 1.5 секунды на сессию (защита от флуда).
   - Лимит размера аудиосегмента: жесткий отсекатель на уровне 256 КБ (при среднем размере 32 КБ).
2. **Запрет произвольных сетевых запросов (No Arbitrary URL Fetch)**:
   - Прокси принимает **только** бинарные данные от клиента в установленной сессии.
   - Сервер **ни при каких условиях** не выполняет скачивание по сторонним URL, переданным извне (полная защита от SSRF).
3. **Allowlist и валидация данных**:
   - Строгая валидация заголовков аудиоконтейнеров (проверка сигнатур Opus/AAC magic bytes).
   - Отклонение неподдерживаемых форматов с кодом `415 Unsupported Media Type`.
4. **Анти-DDoS и защита очередей**:
   - При переполнении очереди воркеров (backpressure) сервер немедленно возвращает клиенту статус `429 Too Many Requests` с заголовком `Retry-After: 3`. Клиент переходит в режим адаптивного пропуска сегментов без падения плеера.

## 5. Политика конфиденциальности и Zero-Telemetry (Zero-Log)

1. **Отсутствие хранения стримов и звука (Ephemeral Memory Processing)**:
   - Аудиосегменты обрабатываются исключительно в оперативной памяти (RAM) и уничтожаются сразу после завершения генерации TTS-ответа.
   - Дисковое сохранение входящих аудиоданных (`retention = 0 sec`) строго запрещено.
2. **Отсутствие идентификации контента**:
   - Сервер не запрашивает и не сохраняет YouTube Video ID, названия трансляций, названия каналов или описания.
3. **Отсутствие персональных данных**:
   - Отсутствие привязки к Google/YouTube аккаунтам, кукам браузера или системным идентификаторам ТВ.
   - Анонимные сессионные токены имеют время жизни только на период непрерывного просмотра.

## 6. Бюджет задержек (Latency Budget) и целевое смещение эфира

Для стабильного живого перевода без заиканий и срывов буфера требуется точный расчет задержек:

| Этап конвейера | Время обработки | Накопительный итог |
|---|---|---|
| Длительность одного фрагмента аудио (Chunk Duration) | 2000 мс | 2000 мс |
| Нарезка и передача на Live Ingestion Proxy (Network RTT) | 150 – 300 мс | 2300 мс |
| Распознавание речи (Streaming ASR) | 800 – 1200 мс | 3500 мс |
| Машинный перевод текста (MT) | 200 – 400 мс | 3900 мс |
| Синтез русской речи (Fast Neural TTS) | 600 – 1000 мс | 4900 мс |
| Передача переведенного сегмента на ТВ | 150 – 300 мс | 5200 мс |
| Буфер безопасности на ТВ (Jitter Cushion) | 4000 – 6000 мс | 10000 – 11200 мс |

### Вывод:
- Полная задержка конвейера (Pipeline E2E Latency) составляет **~10.0 – 11.5 секунд**.
- **Целевое смещение воспроизведения (Live Target Offset Policy)**:
  Введенный в Patch #4 профиль **BALANCED (15 секунд)** идеально вмещает конвейер живого перевода с комфортным запасом устойчивости (3.5 секунды) против сетевых колебаний.
  - Профиль `LOW_LATENCY (6с)` — недостаточен для живого нейросетевого перевода (возможен только для исходного англоязычного потока без перевода).
  - Профиль `BALANCED (15с)` — оптимальный режим для SmartTube VOX Live Translation.
  - Профиль `STABLE (25с)` — резервный режим для медленных сетей и Wi-Fi со слабым сигналом.

## 7. Поведение при изменении скорости воспроизведения (Playback Speed)

В отличие от VOD-контента, где ускорение до 1.25x – 2.0x не ограничено живым потоком, для прямых трансляций действуют строгие физические ограничения:
1. **При скорости > 1.0x на прямом эфире**:
   - Плеер неминуемо нагоняет Live Edge (границу прямого эфира) со скоростью `(Speed - 1.0) * Time`.
   - При приближении к краю эфира менее чем на 5.0 секунд (`SHORT_LIVE_BUFFER_MS`), буфер живого перевода исчерпывается, что приводит к периодическому буферизированию (rebuffer stall).
2. **Стратегия контроллера скорости для прямого эфира с переводом**:
   - Если включен живой перевод, скорость плеера фиксируется на **1.0x**.
   - Допускается кратковременное ускорение до **1.05x – 1.10x** исключительно как механизм плавной ликвидации накопившегося отставания (Clock Drift Catchup), когда отставание превышает 25 секунд.
   - Замедление до **0.95x** используется при временном проседании сети для бесшовного накопления буфера без показа спиннера.

## 8. Клиентская архитектура SmartTube VOX (готовность ядра)

Ядро клиента SmartTube VOX уже подготовлено к интеграции Controlled Live Backend в рамках Patches #1–#4:
- `VoxLivePlaybackMonitor`: ведет мониторинг здоровья живого потока, фиксирует ребуферы и сетевые ошибки.
- `VoxPlaybackBufferPolicy`: обеспечивает 15 секунд минимального буфера и 30 секунд максимального буфера для живых трансляций.
- `DashDefaultLoadErrorHandlingPolicy`: ликвидирует 60-секундный блэклистинг треков при временных 404 на границе эфира.
- `VoxTranslationCapabilities`: объявляет текущие возможности (`LIVE_BACKEND_CAPABILITY = VOD_ONLY`).
- `VoxTranslationQueue` & `VoxTranslatedBuffer`: готовы к приему сегментированного аудиопотока с точной меткой времени `ptsMs`.
