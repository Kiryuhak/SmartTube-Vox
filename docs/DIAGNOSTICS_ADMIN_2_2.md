# Diagnostics Admin 2.2

Админка VOX показывает анонимные диагностические отчёты и помогает разбирать повторяющиеся инциденты. Обновление не создаёт релиз Android, тег или GitHub Release.

## Интерфейс

- Пять прежних статусов сохранены: `NEW`, `IN_PROGRESS`, `RESOLVED`, `KNOWN_ISSUE`, `IGNORED_TEST`. Статус меняется в строке таблицы без открытия отчёта. При ошибке значение возвращается, результат показывается в уведомлении.
- Кнопка «Заметка» открывает компактное поле ввода; последняя заметка видна в строке. История статусов и заметок находится в панели отчёта.
- «Открыть» показывает правую панель. На узком экране она занимает всю ширину. Внутри есть краткий вывод, устройство, события, операции и технический JSON. Кнопки копируют краткий текст и структурированный текст для анализа; JSON скачивается после очистки.
- Фильтры: платформа, статус, назначение, категория, важность, версия, устройство, наличие заметок и повторов, «Требует внимания». Поиск обрабатывается через подготовленные SQL-запросы. Доступна сортировка и постраничная загрузка по курсору для новых отчётов; ручное и автоматическое обновление каждые 45 секунд не перезагружают страницу.
- Карточки метрик переходят к соответствующему списку. Удаление всех логов отделено от обычных действий и требует слова `УДАЛИТЬ`.
- Вкладка «Частые проблемы» группирует отчёты по сигнатуре и показывает версии, количество, первое/последнее появление, статус проблемы и поля версии, патча и коммита исправления. Проблема с исправленной версией повторно открывается только при отчёте той же или более новой версии.

## Данные и диагностические события

Worker приводит события к полям `timestamp`, `category`, `subsystem`, `stage`, `event`, `severity`, `result`, `errorCategory`, `safeContext`, `repeatCount` и при наличии `durationMs`. Старые события `level`/`code` поддерживаются. Поля `safeContext` разрешаются по белому списку. На Android повторяющиеся события ниже уровня ERROR объединяются в десятисекундном окне с `repeatCount`; ERROR остаются отдельными событиями. Кольцевой буфер при переполнении сначала удаляет низкоприоритетное событие. Исходная политика хранения сервера остаётся 30 дней.

Сигнатура для структурированных событий складывается из категории, подсистемы, этапа, категории ошибки, безопасного класса исключения и типа источника. Старый формат сигнатуры поддерживается для прежних отчётов. Сводка вычисляется детерминированно, без вызова модели. Важность имеет уровни `INFO`, `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` и определяется кодом события, повторениями и исходным уровнем журнала. `UNKNOWN` возможен, когда входные данные действительно не содержат признаков ошибки.

## API

Используются существующие маршруты `/v1/admin/*`; алиасы `/api/admin/*` доступны для новой интеграции. Все маршруты требуют аутентификации.

| Маршрут | Назначение |
| --- | --- |
| `GET /v1/admin/reports?limit=50&cursor=…` | Список, фильтры и `nextCursor` |
| `GET /v1/admin/reports/:id` | Отчёт, заметки, история статусов, число похожих |
| `PATCH /v1/admin/reports/:id` | Статус, заметка, необязательная причина |
| `POST /v1/admin/reports/:id/notes` | Быстрая заметка |
| `GET /v1/admin/issues` | Сгруппированные проблемы |
| `PATCH /v1/admin/issues/:signature` | Статус проблемы и реквизиты исправления |
| `GET /v1/admin/stats` | Агрегированные метрики |
| `GET /v1/admin/reports/changes?cursor=…` | Журнал изменений для будущей автоматизации |

Курсор изменений — возрастающий числовой `id`. Автоматический triage и автоматический перевод в `RESOLVED` не включены. Для браузерного входа используется POST `/admin/session`: сервер выдаёт подписанную cookie на восемь часов (`HttpOnly`, `Secure`, `SameSite=Strict`). Секрет не передаётся в URL и не хранится в cookie. API-клиенты могут использовать `Authorization: Bearer` по HTTPS.

## Безопасность и миграция

Миграция `0003_admin_22.sql` только добавляет поля и таблицы. Она не сбрасывает отчёты, статусы или старые `developer_notes`; новые таблицы содержат историю статусов, заметки, проблемы, аудит и курсор изменений. Исторические отчёты без новых полей остаются доступны. Перед применением к production нужно убедиться, что миграции `0001` и `0002` уже применены; после применения проверить количество отчётов и все четыре известные записи без изменения их статуса.

Worker отклоняет запрещённые ключи при приёме и очищает вложенные значения при выдаче/экспорте. HTML-значения экранируются, CSP разрешает только внешний `/admin/app.js`. Секрет администратора не выводится на фронтенд, в JSON, логи или скриншоты. Запросы к БД используют bind-параметры; значения сортировки берутся из фиксированного списка.


После полного PASS и проверки доступа Cloudflare: сначала применить миграцию `0003` к D1, затем опубликовать Worker из `services/vox-diagnostics`. Production smoke должен быть только на чтение: `/admin`, вход, таблица, панель отчёта, заметки, проблемы, метрики и фильтры. Реальные `RESOLVED` отчёты не переключать ради теста. Отдельный релиз приложения не требуется.
